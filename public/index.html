STEP 1

Access 走标准 OIDC 协议，找到你的租户专属入口 *.sso.服务域名。

STEP 3

签发身份进门

为什么需要

钉钉不是标准 OIDC，直连必挂

Cloudflare Access 原生支持 Google、GitHub、Okta……唯独没有钉钉。因为钉钉的「OAuth2」有三处和规范对不上，标准 OIDC 客户端根本走不通：

token 端点

只收 JSON camelCase 请求体，而所有标准实现发的都是表单或 Basic 头。

用户信息端点

要求专用的 x-acs-dingtalk-access-token 头，不认标准的 Bearer。

回调参数

授权码塞在 authCode 参数里，不是规范里的 code，标准端直接找不到。

桥接服务在中间做完整翻译：对钉钉说钉钉的话，对 Cloudflare 说标准 OIDC。这套翻译已经过真实企业环境全链路验证。

安全设计

按对外服务标准做的底层

  • 租户隔离每个组织独立子域名、独立签名密钥对，互不可见。
  • 组织准入钉钉返回的 corpId 与白名单比对，外部钉钉账号扫码无效。
  • 凭证保管钉钉密钥 AES-GCM 加密落库；OIDC 密钥只存哈希，明文仅开通时展示一次。
  • 防重放授权码一次性且 2 分钟有效，重复提交直接拒绝。
  • 密钥轮换签名密钥支持在线轮换，新旧双活，登录不断线。
  • 隐私最小化只透传登录所需的 unionId 与昵称，不落库手机号、头像等个人信息。

常见问题

接入前常问的

员工登录时用什么账号？
就用钉钉：员工的钉钉 App 扫码或点确认即完成登录，没有新密码、不用记别的。身份邮箱按 unionId@dingtalk.local 生成，可直接用在 Access 策略白名单里。
会影响现有登录方式吗？
不会。钉钉登录作为一个新登录方式挂到 Access 应用上，原有的一次性邮箱 PIN、其他 IdP 全部保留，登录页多个按钮而已，随时可切换。
Test 按钮报错怎么办？
九成是五个字段里有 URL 填错，逐字核对三个端点的结尾（/authorize、/token、/jwks，无尾斜杠）。完整的报错对照表在接入文档里。
服务的可用性怎么保障？
服务跑在 Cloudflare 全球边缘网络上，与你的 Zero Trust 同源同网；登录链路有健康拨测与告警，签名密钥可在线轮换，单租户问题不影响其他组织。
